# Raspberry Pi → Collector: delivery protocol

This is the contract between the Raspberry Pi software and the data collector
(`run_data_collector`). Read it before writing or changing the Pi code. The
server side is described in [`README.md`](README.md); the implementation is
`src/collector_server.rs`, and `tests/collector_test.rs` shows every case below
as an executable example.

## Goals

1. **No lost events.** If the network drops, the Pi keeps the event and sends it
   again later.
2. **No duplicate events.** Sending the same event several times, for example
   because the reply was lost, stores it once.
3. **The Pi knows for certain** that the server stored exactly what the Pi sent.

## How it works, in one paragraph

The Pi gives every event a unique **`event_id`** (a UUID) when the event is
created, and sends it inside the JSON. The server stores the event under that id
and computes the **SHA-256 of the exact bytes of the request body**, which it
stores and returns. The Pi computes the same SHA-256 over the bytes it sent. If the two
hashes match and the status is `200`, the event is safely stored and the Pi may
delete its local copy. Anything else means: keep it and try again (or see the
table for the few cases where retrying will not help).

## Request

```
POST https://<server>/api/alpr/event
Content-Type: application/json
X-Collector-Token: <shared secret>
```

The body is a JSON object with exactly these fields:

| Field         | Type   | Notes |
|---------------|--------|-------|
| `event_id`    | string | **A UUID, generated by the Pi once per event and reused for every retry of that event.** Any standard textual form is accepted (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`). The server stores it lowercase with hyphens. Anything that is not a UUID is rejected with `400`. It is used in file names, which is why it is validated strictly. |
| `camid`       | string | Must match a camera registered on the server (`camera.id`). Unknown cameras are rejected with `422`. |
| `date`        | string | When the vehicle was seen. **RFC 3339 with an offset**, e.g. `2026-10-09T16:44:25.443+08:00` or `2026-10-09T08:44:25.443Z`. The server converts it to `+08:00` for storage. |
| `plate`       | string | The recognised plate text. |
| `image`       | string | The scene image, **base64** (standard alphabet, with padding), a JPEG. |
| `plate_image` | string | The cropped plate image, base64 JPEG. |

Maximum body size is **20 MB** (larger gets `413`). Base64 makes images about a
third bigger, so this allows roughly 14 MB of raw JPEG data per event in total.

The `X-Collector-Token` header is checked by nginx, not by the collector. A
missing or wrong token gets `401` from nginx. Always use `https://`, because the
token is only secret on an encrypted connection.

### The most important rule: send the same bytes every time

The server hashes **the raw bytes of the body**, not the parsed JSON. So:

- **Serialise the event to JSON once, keep those exact bytes, and send those
  same bytes on every retry.** Do not rebuild the JSON for a retry. Different key
  order, spacing or number formatting produces different bytes, a different hash,
  and a `409` (see below).
- Compute the hash over **exactly the bytes you pass to the HTTP client**, after
  any encoding, and before the HTTP layer. (HTTP compression such as gzip is not
  used by this protocol. Do not compress the request body.)
- The simplest robust design: when an event happens, write
  `<event_id>.json` to local disk (the final request body), and have the sender
  read that file and POST its bytes. The file is both the retry queue and the
  source of the hash.

## Response

### Success: `200`

The body is JSON (`Content-Type: application/json`):

```json
{
  "event_id": "49ab6e94-d7ae-4952-a0d2-d0fe89d25771",
  "content_hash": "d8782efe5370801eb5d10149482fb6cdca6ad8f6826baefb4b4a295cf5d1239a",
  "duplicate": false
}
```

| Field          | Meaning |
|----------------|---------|
| `event_id`     | The id the server stored (lowercase, hyphenated). |
| `content_hash` | Lowercase hex SHA-256 of the request body bytes the server received. 64 characters. |
| `duplicate`    | `false`: this request stored the event. `true`: the event was **already** stored by an earlier request (for example you are retrying because the first reply was lost). |

**`200` is returned for both** a first delivery and a repeat. The Pi does not
need to treat them differently: in both cases the event is stored. (`201` is
deliberately not used, so that the Pi has only one success code to check.)

**The Pi must verify the receipt before deleting its copy of the event:**

```
delivered  ==  status == 200
           and response.event_id     == the event_id it sent
           and response.content_hash == sha256_hex(the bytes it sent)
```

If the status is `200` but the hash does **not** match, the data was changed in
transit or something is wrong. Do **not** delete the event. Log it loudly and
retry; if it persists, it is a bug to investigate.

### Errors and what the Pi should do

Error bodies are short **plain text**, not JSON.

| Status | Meaning | Retry? |
|--------|---------|--------|
| `200`  | Stored (new or duplicate). Verify the hash as above. | No, once verified |
| `400`  | Malformed JSON, missing field, `event_id` not a UUID, or bad `date`. | **No.** The same bytes will always fail. Fix the bug. Keep the event aside (dead-letter) and alert. |
| `401`  | Missing/wrong `X-Collector-Token` (from nginx). | **No** until the token is fixed. Keep the event. |
| `403`  | Wrong HTTP method (from nginx). | No. A Pi bug. |
| `404`  | Wrong URL. | No. A Pi bug. |
| `409`  | `event_id` already exists with **different** content, or the stored event predates this protocol and cannot be compared. | **No.** It means the Pi reused an id for different bytes (see "Pitfalls"). Keep the event aside and alert. Never answer a `409` by silently dropping the event. |
| `413`  | Body over 20 MB. | No. Send smaller images. |
| `422`  | `camid` is not a registered camera. | **Later**: it succeeds once the camera is registered on the server, with the **same bytes and event_id**. Keep the event and retry slowly. |
| `429`  | Too many requests (nginx rate limit, 10 per second per IP). | Yes, after a delay. |
| `500`, `502`, `503`, `504` | Server-side or proxy failure (database, disk, restart). | **Yes**, with backoff. The same bytes are safe to resend. |
| no response / timeout / connection error | The request may or may not have been stored. | **Yes**, with backoff, with the **same bytes**. This is exactly the case the protocol is designed for. |

### Why retrying after a timeout is safe

If a request times out, the server may have stored the event and only the reply
was lost. Resending the same bytes returns `200` with `"duplicate": true` and the
same `content_hash`, and **no second copy is stored**, so the Pi cannot create
duplicates by retrying. The check is safe even if two retries arrive at the same
instant.

## Retry behaviour (recommended)

- Keep every undelivered event on disk, and keep a queue ordered oldest first. The
  queue must survive a reboot or power loss.
- Use **exponential backoff with jitter**, e.g. 2 s, 4 s, 8 s ... capped at a few
  minutes, so that a recovering server is not flooded by every Pi at once.
- Use a request timeout (e.g. 30-60 s). Large bodies over a slow link need time,
  but nginx closes the connection if the body upload stalls for 60 s.
- Delete the local copy **only** after a verified `200` (status, `event_id` and
  hash all match).
- Events do not need to be delivered in order. The server orders by `date`.
- Do not send many events in parallel on a weak link. One at a time is fine.

## Computing the hash

SHA-256 over the raw body bytes, written as **lowercase hexadecimal**.

Test vectors, so you can check your implementation:

| Input bytes | SHA-256 (lowercase hex) |
|-------------|--------------------------|
| `abc` (3 bytes) | `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` |
| empty | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |

On the command line: `sha256sum event.json`.

### Example (Python)

```python
import hashlib, json, uuid, base64, requests

SERVER = "https://collector.example.com/api/alpr/event"
TOKEN = "the-shared-secret"

def make_request_body(camid, date_rfc3339, plate, scene_jpeg: bytes, plate_jpeg: bytes):
    """Build the event ONCE. Save these bytes; resend exactly these bytes on retries."""
    event = {
        "event_id": str(uuid.uuid4()),   # generated once, here, never again for this event
        "camid": camid,
        "date": date_rfc3339,
        "plate": plate,
        "image": base64.b64encode(scene_jpeg).decode("ascii"),
        "plate_image": base64.b64encode(plate_jpeg).decode("ascii"),
    }
    return json.dumps(event).encode("utf-8"), event["event_id"]

def deliver(body: bytes, event_id: str) -> str:
    """Returns 'delivered', 'retry', or 'reject' (do not retry; keep and alert)."""
    try:
        r = requests.post(
            SERVER,
            data=body,                    # the stored bytes, unchanged
            headers={"Content-Type": "application/json", "X-Collector-Token": TOKEN},
            timeout=60,
        )
    except requests.RequestException:
        return "retry"                    # timeout / no connection: safe to resend

    if r.status_code == 200:
        ack = r.json()
        ok = (ack["event_id"] == event_id
              and ack["content_hash"] == hashlib.sha256(body).hexdigest())
        return "delivered" if ok else "retry"   # mismatch: keep it, never delete
    if r.status_code in (422, 429) or r.status_code >= 500:
        return "retry"
    return "reject"                       # 400, 401, 403, 404, 409, 413, ...
```

## Pitfalls

- **Rebuilding the JSON on retry.** Python's `json.dumps` on a dict is stable, but
  regenerating the event may change something (a fresh timestamp, a new
  `event_id`). A new `event_id` means a **second event**. Same `event_id` with
  different bytes means `409`. Always resend the saved bytes.
- **Reusing an `event_id` for a different event.** Generate a new UUID for every
  new event. Never derive it from something that can repeat (like the plate text
  or a counter that resets after a reboot).
- **Different spellings of one UUID.** `ABC...` and `abc...` are the same UUID to
  the server, but they are different bytes. Always send the exact bytes you
  hashed, and keep the same spelling on retries.
- **Hashing the wrong thing.** Hash the bytes that go on the wire, not the dict,
  not the pre-base64 images, and not the response.
- **Compressing the request body.** The server does not decompress it.
- **Treating `409` as "already delivered".** It is not. `duplicate: true` on a
  `200` is how the server says "already delivered". A `409` means your data and
  the stored data disagree.

## Quick manual test

```sh
BODY='{"event_id":"11111111-2222-4333-8444-555555555555","camid":"CAM1","date":"2026-10-30T10:00:00Z","plate":"ABC1234","image":"/9j/4AAQ","plate_image":"/9j/4AAQ"}'
echo -n "$BODY" | sha256sum        # what the Pi computes
for i in 1 2; do                   # the second reply says "duplicate": true
  curl -s -X POST https://collector.example.com/api/alpr/event \
       -H "X-Collector-Token: $TOKEN" -H "Content-Type: application/json" \
       --data-binary "$BODY"; echo
done
```

(Use `--data-binary`, not `-d`: `-d` can strip newlines, which would change the
bytes and therefore the hash. Note `echo -n` so that no trailing newline is added
to the hashed text.)

## Existing data

Events stored before this protocol existed (for example those copied by
`migrate_data`) have no hash. They can never be reported as duplicates. If a Pi
sends the `event_id` of one of those rows, it gets `409`. In practice this does
not happen, because those rows have ids that were not issued by a Pi.
